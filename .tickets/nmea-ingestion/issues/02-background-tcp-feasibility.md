# 02 — Feasibility gate: a TCP socket that survives the screen going off

Type: research
Status: resolved
Blocked by: —
Map: [map.md](../map.md)

## Question

**This is a gate.** Founding decision 6 requires recording to continue with the
phone's screen off and the app backgrounded, for up to ~3 hours. If that can't
be done, the capture design changes shape entirely and several tickets below
are invalidated.

Can an **Expo SDK 55 / React Native 0.83** Android app hold an open TCP socket
and keep writing parsed samples to SQLite while backgrounded with the screen
off?

1. **The mechanism.** Android kills or freezes background JS quickly. The
   standard escape is a **foreground service** with a persistent notification.
   Establish which of these actually works under Expo with a dev build (the app
   already uses a custom dev client, so config plugins and native modules are
   available — it is not restricted to Expo Go):
   - `expo-task-manager` + a background-capable module
   - a third-party foreground-service library
     (e.g. `react-native-background-actions`) and whether it has an Expo
     config plugin
   - `expo-location`'s own background/foreground-service mode — the app
     **already** has `expo-location` installed with
     `locationAlwaysAndWhenInUse` configured. Does its foreground service keep
     the JS runtime alive such that an unrelated TCP socket keeps running, or
     does it only service location callbacks?
   - a purpose-written config plugin / native module
2. **The socket.** Which TCP client library works here —
   `react-native-tcp-socket` is the obvious candidate. Is it maintained, does
   it work on RN 0.83 / New Architecture, and does it keep its socket open
   inside a foreground service?
3. **New Architecture.** Establish whether the app runs the New Architecture
   (check `app.config.js` / `gradle.properties` in the repo) and whether the
   candidate libraries support it. This eliminates options quickly.
4. **Android version constraints.** Foreground service types became mandatory
   in Android 14 (`android:foregroundServiceType`). Which type legitimately
   covers "reading data from a boat instrument over WiFi"? `dataSync` and
   `connectedDevice` are both plausible; getting this wrong is a Play Store
   rejection, though for a personal-use app that may not bite.
5. **Doze and battery optimisation.** Does a foreground service survive Doze
   for 3 hours, or does the WiFi radio get parked anyway? Is a WiFi lock
   (`WifiManager.WifiLock`) also needed?
6. **The fallback.** If none of this works cleanly, what is the honest
   alternative — screen-on with a wake lock and a dimmed display, a separate
   always-on recording device, or something else?

Deliver a recommendation with a named library set and the config-plugin
changes required, plus a clear verdict on whether the gate is passed.

## Answer

**VERDICT: GATE PASSED, WITH CAVEATS.** A 3-hour screen-off backgrounded TCP
capture is achievable on this exact stack via an Android **foreground service of
type `connectedDevice`**. Founding decision 6 stands. But there is **no drop-in
library**, and the verdict is provisional until a device spike — see `13`.

Full findings with citations:
[`research/02-background-tcp-feasibility.md`](../research/02-background-tcp-feasibility.md).

### Repo facts established (verified, not assumed)

Expo 55.0.4 / RN 0.83.2 / React 19.2 / **New Architecture ENABLED**
(`android/gradle.properties:38`) / Hermes / minSdk 24, targetSdk 36, compileSdk
36. `android/` is committed but regenerated by `prebuild --clean`. **The current
manifest has no `FOREGROUND_SERVICE*` permissions at all** — `expo-location`'s
plugin only adds them when `isAndroidForegroundServiceEnabled` is passed, and
`app.config.js` doesn't pass it. Today the app cannot start any foreground
service.

### The decisive mechanism

Not Doze — the **cached-apps freezer**. AOSP is explicit: *"If all processes for
a particular app are frozen, the system terminates any active TCP sockets
maintained by the app"*, frozen 10s after entering cached state on Android 14+.
A foreground service is the named escape, and with one the power-management
table gives **Network: No restrictions**.

### Recommended stack

- `react-native-tcp-socket@^6.4.2` — device-proven on RN 0.83 New
  Arch/bridgeless/Hermes; legacy bridge module working through RN's interop
  layer, which 0.82's release notes commit to keeping.
- A **local Expo module** (`npx create-expo-module --local`) hosting the
  foreground service. Spike first with `react-native-background-actions@4.1.0`
  (a `HeadlessJsTaskService`; 4.1.0 added `foregroundServiceType`), then port —
  its author announced in April 2026 that he has left the RN ecosystem, New-Arch
  support is unverified on 0.8x, and it has no Expo config plugin.
- Full `app.config.js` plugin code is in the research doc.

### Four findings that change the design, not just the implementation

1. **JS timers do not survive backgrounding.** Verified against this repo's own
   RN source: `JavaTimerManager.onHostPause()` calls `clearFrameCallback()`,
   removing the Choreographer callback that drives `setTimeout`/`setInterval`.
   **The capture pipeline must be event-driven off socket `data` events plus a
   native Kotlin tick — no `setInterval` anywhere.** This directly constrains
   `05`'s sampling model, and `09` and `11`.
2. **Use `connectedDevice`, never `dataSync`.** Android 15 caps `dataSync`
   foreground services at **6 hours per 24h** and then kills them via
   `Service.onTimeout()`; targetSdk 36 means no grace period. `connectedDevice`
   has no cap and is documented as covering *"external devices that require a …
   network connection"*. Prerequisite is `CHANGE_WIFI_STATE` — install-time, no
   user prompt.
3. **WifiLock is a dead API — drop it.** Current AOSP: `WIFI_MODE_FULL` and
   `SCAN_ONLY` are *"non-functional"*, `FULL_HIGH_PERF` folds into
   `FULL_LOW_LATENCY`, and `FULL_LOW_LATENCY` is *"only active when the screen
   is on"* and *"only when the acquiring app is running in the foreground."*
   No WifiLock does what this ticket's question 5 assumed. None is needed.
4. **Pass `interface: 'wifi'` on connect.** An Android-only option in
   `react-native-tcp-socket`. The Zeus 3's AP has no internet, so without
   pinning, Android keeps the default route on cellular — a "works at the
   marina, fails at sea" bug. **This substantially answers `11`'s question 3.**

### Rejected: `expo-location`'s foreground service

It would *mechanically* work — a real `startForeground` service holding the
process non-cached, and an unrelated socket in the same process would survive.
Rejected anyway: it doesn't fix the timer problem, its lifetime is owned by the
location task, Expo has open long-run FGS bugs against it (#47595, #14076), and
it costs `ACCESS_BACKGROUND_LOCATION` for no benefit.

### Risks and what stays open

- **OEM battery managers are the real killer** — gate on
  `isIgnoringBatteryOptimizations()` and persist continuously, so a kill costs
  minutes rather than the race.
- **Unresolved: does `Choreographer` deliver frames with the display off?** The
  existence of the `react-native-background-timer` genre implies not; field
  reports contradict each other. The recommended design routes around it for
  ~10 lines of Kotlin, but it's the most important unknown — `13` step 4 is
  designed to answer it.
- Also unestablished: whether `react-native-background-actions@4.1.0` builds on
  AGP 8.12, and whether *any* 3-hour screen-off report exists for this exact
  combination. None was findable.
- Eventual removal of RN's legacy interop layer would strand
  `react-native-tcp-socket`.
